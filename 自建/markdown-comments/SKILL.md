# Markdown 批注

把 `chaos:` 及兼容写法视为用户写在 Markdown 中的高优先级决策批注。正文直接修改由 Git diff 捕捉，批注说明决策及理由；二者共同构成一次审阅。

## 识别规则

有效标记兼容以下四种小写写法：`chaos:`、`chaos：`、`chao:`、`chao：`。其中 `chao` 是真实审阅中常见的简写或漏写，不得因此忽略用户决策。

有效批注满足：

- 标记位于独立批注行，或位于正文行尾；标记前可以有 Markdown 容器、缩进或正文。
- 独立批注行锚定紧邻的上一正文块；连续多条独立批注均锚定该正文块。
- 行尾批注锚定标记前的同一行正文；从标记开始直到行尾均属于批注，标记前内容仍是正文。
- 标记不在 fenced code block（由反引号或波浪线围成的代码块）内。若上下文明显是在讲解语法而不是表达审阅决定，不当作待处理批注；无法判断时保留并询问用户。

需要精确到词句时，批注可引用原文。处理行尾批注时，删除标记及其后内容，但必须保留标记前的正文与必要的行尾空白清理。

```markdown
负责告警治理和根因定位。
chaos: “负责”改成“主导”，语气太被动。
```

## 触发与被动发现

在以下任一情况使用本 Skill：

1. 用户要求“处理批注”“按批注改一版”“继续改简历”等。
2. Agent 在任何 Markdown 中发现有效 `chaos:` / `chao:` 批注，即使当前任务不是处理批注。
3. Agent 在 Git 仓库中生成或修改供用户审阅的 Markdown 成品，例如简历、报告或方案。普通 README、代码文档和临时笔记仅在出现有效批注或用户明确要求时触发。

被动发现批注时：

- 把它识别为用户决策，不当作正文引用、改写或总结。
- 若当前任务未授权处理该文档，原样保留并提醒用户，不自动执行。
- 若准备修改同一文档，先处理现有批注或向用户确认；不得覆盖生成新版本。
- 只有用户明确要求处理仓库全部批注时，才扫描全部 Markdown；否则只处理用户指定或当前对话明确指向的文档。

## 优先级与铁律

1. 有效批注是最高优先级决策来源，高于 Agent 风格偏好和文档既有惯例。不得静默忽略、弱化或变相改写。
2. 用户对正文的直接修改原样保留。若正文 diff 与批注冲突，以带显式理由的批注为准；多条批注彼此冲突时停止并询问用户。
3. Agent 若认为决策存在问题，优先先确认；若用户已要求执行，则照做，并把保留意见放入决策日志的 `[agent 建议]` 和 commit 的“agent 执行说明”，不得伪装成用户决策。
4. 每次生成或修改供审阅的文档后，必须单独创建一次交稿 commit。不得把交稿与其他文件、其他任务或尚未处理的工作区改动混为一个 commit。
5. 禁止重写相关 Git 历史：不 rebase、不 force push、不 amend 既有交稿或批注处理 commit。
6. 只精确暂存本轮目标文档及其决策日志；禁止 `git add .`、`git add -A`、`git commit -a`。
7. 不自动 push。只有用户明确授权当前仓库和目标分支后才能推送。

## 交稿协议

同一文档只能有一个未完成审阅周期。交稿 commit 的主题固定为：

```text
agent: <仓库相对文档路径> v<N> [YYYY-MM-DD]
```

例如：

```text
agent: resume.md v3 [2026-08-23]
```

版本规则：

- Agent 每生成一个新的可审阅版本，`N` 加一；首次合规交稿为 `v1`。
- 处理该版本的批注沿用同一个 `v<N>`，不递增。
- 文件中仍有有效批注时，不得创建下一版交稿 commit。

提交前检查工作区，只精确暂存目标文档。若目标文档含来源不明或与当前任务无关的修改，先停止并确认，不能把它们冒充为本次交稿。

## 处理批注的固定流程

### 1. 确定目标和审阅基线

只处理用户指定或当前对话明确指向的文档。定位该文档最近一次符合交稿主题格式、且实际修改过该文档的 commit；以文档为准，不依赖 Agent 身份。

可以先查看：

```bash
git log --format="%H%x09%s" -- <目标文档>
```

若不存在合规交稿 commit，不得猜测基线：保留当前正文和批注，向用户说明无法可靠区分交稿内容与后续修订。用户确认后才可采用指定 commit，或把当前状态建立为新的基线。

### 2. 读取用户直接修订

使用下面的比较方式，不要写成只比较两个 commits 的 `<交稿commit>..HEAD`：

```bash
git diff <交稿commit> -- <目标文档>
```

该命令比较交稿 commit 与当前工作区，可覆盖后续 commits、暂存区和未暂存修改。直接修订必须保留；不要替用户猜测未写在 `chaos:` 中的理由。

### 3. 扫描并解释批注

扫描目标文档全部有效批注，区分独立行与正文行尾标记并建立锚点。批注文字是用户决策和理由；引用原文的批注优先按所引词句精确定位。

### 4. 应用修改

- 落实所有当前可完成的批注，同时保留用户正文修订。
- 只有完全落实的批注才删除。独立批注删除整行；行尾批注只删除标记及其后内容，保留同一行正文。
- 需要外部数据、事实或权限才能完成的批注不得编造；原始批注必须保留，并在决策日志和 commit 中标记待处理。
- 多条批注冲突、锚点已经失效或意图无法确定时，保留原批注并询问用户。
- 处理后再次扫描，确认已完成批注已删除、未完成批注仍原样存在。

### 5. 追加长期决策日志

同一逻辑文档长期共用一个稳定的 decisions 日志，不因文件改名、候选稿或 V2/V3/V4 等版本升级而重复创建。先查项目 `AGENTS.md`、当前 Issue、已有 decisions 文件或用户明确指定的映射；已有映射必须沿用。只有项目没有约定且文档也不属于已知版本家族时，才默认使用同目录 `<basename>.decisions.md`。

例如，一组 `resume-v2-01.md`、`resume-v2-02.md`、`resume-v3.md` 可以统一写入 `resume.decisions.md`；一个独立的 `方案.md` 可默认写入 `方案.decisions.md`。不要仅凭当前物理文件名为每个版本新建日志。

日志只追加，不覆盖历史。标题应包含日期和用户可识别的逻辑版本或审阅阶段，例如：

```markdown
## 2026-08-23 V2 → V3 融合

- [用户决策] 砍掉 2019 年前经历：聚焦近五年，HR 平均只看 30 秒
- [用户决策] “负责”改成“主导”：语气太被动
- [用户决策·待处理] 补充线上准确率：需要取得真实评测数据
- [agent 建议] 摘要段同步更新（已执行）
```

提炼会影响后续版本的语义、取舍和理由。纯错别字或一次性排版无需强行上升为长期决策；若批注意味着跨文档通用偏好，在日志中记录本次影响，并提醒用户将通用规则写入项目 `AGENTS.md`，未经授权不要自行修改全局规则。

### 6. 单独提交

精确暂存目标文档和实际发生变化的决策日志，检查 staged diff 后单独 commit。主题和正文固定分层：

```text
处理批注: <仓库相对文档路径> v<N> [YYYY-MM-DD]

用户决策 (chaos:, 高优先级):
- “负责”→“主导”：语气太被动
- 砍掉 2019 年前经历：聚焦近五年
- [待处理] 补充线上准确率：等待真实评测数据

agent 执行说明:
- 按第一条决策同步修改摘要段措辞
- 修正两处标点
```

“用户决策”逐条忠实引用批注中的决定和理由；Agent 主动做的同步修改、机械修正和保留意见只能进入“agent 执行说明”。用户正文修订由 diff 保留，其理由已经由对应批注表达，不再创建第三个 commit 章节。

## 收尾检查

- 目标文件和决策日志之外的文件没有被暂存或提交。
- 所有已落实批注均从正文删除；所有未落实批注仍原样存在。
- 用户直接修订没有被回退或重新措辞。
- 决策日志只追加，用户决策与 Agent 建议标识清楚。
- commit 版本号与交稿版本一致，日期使用执行当天日期。
- 若仍有未处理批注，明确告诉用户本轮未完成项；在其解决前不创建下一版交稿。
